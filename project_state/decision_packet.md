## Owner implementation boundary

Issue #145 is a bounded presentation-truth repair on canonical planning. The Task API already returns raw validation fields, but its derived `frontend_task` incorrectly maps successful validation to `PENDING` when failure classification is empty and uses fixture-specific READY_FOR_HUMAN next-action wording. Frontend normalization also defaults missing derived test status to `PENDING` rather than preferring raw validation truth.

After `PRE_EXECUTION_AUTHORIZED`, change only the four allowed product/test paths. Backend mapping must make `validation_exit_code` authoritative when present (`0 -> PASS`, nonzero -> `FAIL`), use `RUNNING` only for the actual `VALIDATING` backend state when no exit code exists, preserve explicit pending/failure behavior otherwise, and make READY_FOR_HUMAN next action executor-neutral. Frontend normalization must defensively prefer raw `validation_exit_code`, then raw `VALIDATING`, then a valid derived frontend status, then `PENDING`.

Do not change TaskStore schema, executor behavior, state transitions, Binding/credential paths, frontend workbench presentation, types, dependencies, or mock-mode fixture semantics. Add exact backend regressions and a new focused frontend test using an OpenCode-shaped HTTP payload without relying on a real model/provider/OpenCode process.

The baseline bug reproduction command is intentionally pre-implementation evidence and must pass before mutation. After any product/test failure, stop for Owner audit; repair_attempt_limit is zero. If `dev-up.ps1` succeeds and any later live probe fails, run the authorized `dev-down.ps1` first to clean exact owned process trees, then stop. No manual name-wide process kill is allowed.

Every required `allowed_commands` entry is literal authority. Missing test node, skipped command, broader substitute, timeout or nonzero exit is failure.
