## 1. Magpie 复用不彻底 —— 部分接受

### 接受的部分

方向正确：账户级"选哪个账户、额度耗尽后在**同一服务内**换账户"本质是**请求级资源调度**，
属于 Magpie 的天然职责；Nerelan 去做这件事会与上游重叠。

### 需要纠正的事实

当前 **Nerelan 并没有调用 Magpie 的任何路由/切换能力**，它对 Magpie 的接入是**只读观测**：

```text
model_access/magpie.py:251-256
  GET /api/hello                    → 版本
  GET /v1/models                    → 模型清单
  GET /v1/magpie/quotas?kept=1      → 账户额度窗口
```

没有任何 `route` / `switch` / `wait` 端点调用。所以当下的真实问题是**职责未划清**，

同时必须承认：`multi_account/scheduler.py` 的账户选择确实**跨到了账户层**。如果本机 Magpie
版本已支持账户内自动切换与 `quota wait`，那么它应退化为：

> **Magpie 在位时的 fallback**：仅当 Magpie 未启用、不可用、或其观测不含该 provider 时才生效。

## 3. 成本优化不是完整经济模型 —— 接受（指标层已修，模型层分阶段）

### 接受

- 列表价 ≠ 增量现金成本；订阅额度是**机会成本**，不是 0。
- API 不等于"只受成本约束"：同样有 RPM/TPM、余额与预算上限 —— 需要容量与限流感知。
- **`cost_per_accepted_change` 的分母/分子口径有偏**：它只把**验收成功**那次运行的成本计入分子，
  失败尝试、重试、规划与验证的消耗全部消失（`orchestration_selector.py:99-131`）。
  一个"成功时便宜、经常失败"的策略会被系统性高估。**这条批评完全成立。**

### 已做（本轮）

新增 `orchestration_selector.all_in_economics(runs)`（**只报告、不改变任何决策**）：

```
unit_cost          = 全部尝试的已知成本 / 独立验收合格的结果数
attempts_per_accepted = 尝试数 / 合格数
failed_cost_share  = （总成本 − 合格成本）/ 总成本
```

口径约束：任一尝试成本未知 → 整体 `None`（未知不能当 0），避免"没上报＝免费"的选择性偏差。
覆盖测试：`test_orchestration_selector.py::test_all_in_cost_counts_failed_attempts` 等 3 例。

> 补充事实：`cost_per_accepted_change` 目前**零生产调用方**（与 `break_even` 同属"孤儿能力"），
> 所以本轮新增指标不改变任何在线决策——这也正是评审所说"经济性还未真正进入决策链"的具体表现。

### 未做（须单独决策）

把 `update_break_even` 的拟合切换到摊薄成本，会**改变选择器优化的目标函数**。这属于
"重写既有算法"，按规范 §9 与 `AGENTS.md` R1/R2 边界，需要 Owner 决策 + 独立评审后才能动。
在此之前，经济性结论必须同时报 `cost_per_accepted`（老口径）与 `cost_per_accepted_all_in`（新口径），
**不允许只引用对结论有利的那一个**。

### 机会成本与限流（P3）

| 维度 | 当前状态 | 计划 |
|---|---|---|
| 增量现金成本 | 有（列表价 USD） | 保持 |
| 额度机会成本 | **无** | P3：以"剩余额度 / 剩余时间"折算影子价格，仅同 provider 内比较 |
| 协调开销 | 无 | P3：planning/review/context 的 token 单独归因 |
| 失败重试成本 | **已可测**（`all_in_economics`） | P3：进决策需决策批准 |
| API 限流/余额 | 部分（`cost_class` 区分） | P2：429/余额不足纳入冷却与准入理由 |

## 4. 自进化只是参数校准 —— 接受边界，不接受"现在就上策略发布系统"

评审建议的六步闭环（执行→采集→候选策略→历史回放→灰度→发布/回滚）方向正确。但顺序要反过来：

- 当前连**可靠的成本口径**都刚补上（见 §3），历史数据里没有失败成本、没有策略版本号；
- 在这个数据面上做"候选策略 + 灰度"，得到的只会是**对噪声的过拟合**。

因此明确：

1. **现在**（P2）：只做参数校准（冷却/退避/权重/`break_even`），全部**有界、可解释、可回滚**。
2. **P3**：补策略**版本化**与**离线回放**（同一批历史 run 跑新旧策略，产出对照表）。

现有"每模式每档 ≥3 次观测"只能当**探索门槛**，不能当"更优"的证明 —— 评审这点接受。

## 5. 容错一致性不足 —— 接受，列为最高风险项

### 接受

- 最危险的不是"任务失败"，而是**旧执行器没死、新执行器又起来了**：同一份文件被两方修改、
  外部副作用被重复触发。
- "本地休眠时进程不能照常发心跳" —— 因此**更频繁的 keepalive 不能解决恢复正确性**，
  它只会把"误判死亡"变成"误判存活"。

### 现状与边界

- `C3（host sleep 恢复后租约不误 fence）` 在规范里**始终标注未闭环**，本轮没有触碰 lease 语义。
  本轮唯一相关改动是空闲等待提示（`idle_wait`，上限 60 s），**不改**租约与 fencing。
- 评审的第二点"不能因为新模块报错就绕过硬约束"，核对结论如下：

| 约束类型 | 实现位置 | 失败时行为 | 判定 |
|---|---|---|---|
| 额度硬准入 | `control_store.prepare_quota_admission` → `quota_reservation.admission`（`control_store.py:1771-1774`） | 抛错即拒绝，任务转 `QUOTA_WAIT` | **fail-closed**，未被新模块绕过 |
| 账户健康预筛 | `goal_service._reroute_guard_skip` → `dispatch.reroute_guard` | 任何异常 → 不跳过（放行重路由） | **fail-open**，但只是**优化提示**：目标账户仍要过上面的硬准入 |
| 模式推荐 / 评分 / 学习 | `dispatch.*` | 异常 → 回退旧默认 | **fail-open**，无资源后果 |

结论：**"可降级的优化"与"不可绕过的约束"已经分离在不同层**，但这一分离此前只存在于代码里、
没有写成规则。已补入规范 §12.3，并要求任何新增接缝**先归类再实现**。

### 必须补的验收（P2）

1. 所有权转移：旧 lease 未过期时，新执行器的写入必须被拒（含"旧执行器仍存活"场景）。
2. 检查点验证：恢复后**不接受**早于最新检查点的产物。
3. 外部副作用幂等：PR 创建、Issue 评论、发布动作按幂等键去重（已有 `idempotency_key`，需故障注入验证）。
4. 休眠恢复：进程休眠 ≥ 2×lease 时长后唤醒，**不得**误 fence 存活执行器，也不得重复派发。
