# CLI-2A Windows named-pipe authenticated transport proof

**Owner architecture:** #1198 / #806. **Platform:** Windows AF_PIPE.
**Classification:** test-only R1 proof of transport possession authentication. It does **not** connect the host to CLI/GoalService and is not an autonomous execution feature.

## What was implemented and actually verified

The isolated `native_pipe_probe.py` module uses Python stdlib `multiprocessing.connection.Listener(family="AF_PIPE", authkey=<host-generated 32 bytes>)`. The test-only host now REQUIRES a trusted-bootstrap-supplied expected client PID and compares it with Windows kernel `GetNamedPipeClientProcessId` on the accepted SERVER pipe handle before reading any request frame. The comparison is fail-closed for malformed handles, unavailable Win32 API, and mismatched kernel PID; caller-provided JSON cannot set it. The host-generated pipe address uses a random 128-bit suffix rather than a known/public fixed name; its key is unrelated to `LocalClientSession` (the browser's existing in-memory credential). Only a trusted in-process bootstrap callback can receive the temporary pipe address/key, and the same instance accepts **at most one** pipe connection, then revokes its own key. This bounds accepted application sessions, not kernel pipe instances: stdlib creates a replacement instance while accepting. The PID check runs only AFTER stdlib authentication returns; it does not protect the authentication exchange.

A client with the correct host-delivered key can complete the Windows pipe HMAC challenge and submit a bounded, duplicate-free one-shot `doctor` frame. The reply is `TRANSPORT_PROOF_ONLY`: `transport_authenticated:true`, `principal_authenticated:false`, `dispatch_permitted:false`, `execution_started:false`. Wrong/missing authorization material is not a route to any handler. Any unknown/malformed operation including `goal.launch` replies `NOT_SUPPORTED`. No Goal, Task, Model, SQLite or private status is touched. There is **no background listener or host bootstrap registration** in this branch.

**Real Windows tests:** `pytest -q tests/platform_v1/test_native_pipe_probe.py tests/platform_v1/test_native_pipe_peer.py` run actual AF_PIPE Listener/Client sessions for a correct key, wrong key, forbidden Goal request, a deliberately failed Win32 attestation and an actual separate Windows process with the **correct** key but the **wrong PID**. The foreign process is rejected before its request is parsed or a response is returned. New real-Windows negative tests inspect a live pipe security descriptor with `GetSecurityInfo` / `GetSecurityDescriptorControl`: stdlib passes NULL security attributes and the resulting DACL is present but not protected. This proves no explicit restricted DACL is installed; it does not enumerate effective rights or prove which foreign SIDs can connect. A spawned isolated test host also receives a connection from the wrong PID without any key response: the client receives the authentication challenge and stalls the host before PID attestation. The test observes the stall for 300 ms, disconnects, checks `AUTHENTICATION_FAILED`, and joins the host; its failure cleanup terminates and joins that disposable process. No blocked daemon thread is used for this negative test. A finite observation demonstrates the stall path, not an infinite-time proof. Other provider-free tests cover input bounds, double fields, forged `principal`/`token` fields, no data reflection, and session delivery revocation. This is a unit/integration transport result only; **not** a user-authenticated CLI or Goal execution acceptance.

## Known security gaps: block live host integration

1. **Windows pipe DACL / trust of the PID:** The new Win32 kernel PID check verifies correlation with an **expected PID supplied by trusted host launch**; it does NOT verify the expected PID's provenance, an executable signature, the SID of its primary or impersonation token, or an Owner-approved Goal. Python stdlib `AF_PIPE` still does not create our own restrictive pipe DACL. A same-user untrusted process could otherwise exploit an insecure bootstrap and credentials. Before production, enforce a restricted Windows pipe security descriptor, verify client token/SID/session and OS-created child identity, then bind to a distinct Owner/scheduler principal; do not treat a matching PID, browser session or HMAC key alone as authorization.
2. **Unauthenticated handshake timeout (confirmed negative test):** `Listener.accept()` / authentication can block if a hostile process connects but never completes the challenge. A 32-byte key is not rate limiting or handshake timeout. The expected-PID check cannot reject this client before authentication because `Listener.accept()` has not returned. Accept itself, authenticated request reads and response writes also lack explicit deadlines. A production listener must enforce an absolute total deadline covering accept, authentication, request and response, bounded total connections and cancellation across shutdown/restart **before it is enabled**. Timing out a supervisor while leaving a blocked daemon thread is not a fix.
3. **Secure key delivery:** `deliver_to_trusted_bootstrap` is an in-process injection seam, NOT implemented OS-level child verification. A final native host must pass a separate temporary key only through a restricted inherited anonymous handle or equivalent OS-verified channel; never print/store key in argv, environment, logs, TaskStore, browser bridge, crash messages or GitHub. Calling the callback with an arbitrary/untrusted receiver is forbidden.
4. **Request scope and replay:** This one-shot fixture only understands a public probe. Actual private or mutating `nerelan-control/v1` requests must go through the strict parser in Draft #1212, a host-verified principal, durable CAS/idempotency and the existing GoalService/ControlStore/TaskStore. A valid request schema, matching pipe secret, or Owner-looking string in JSON NEVER grants a Goal window.
5. **Restart/fencing:** A new host generates a new key and pipe; it cannot trust previously running Agents, old approved Goal windows or unknown external jobs. The three unresolved legacy ACTIVE Claims (#1206) still require receipt reconciliation. Exact user-approved Goal/revision/executor (#1207) and real integrated Codex smoke (#1202) remain blocked.

## Decisions and next steps

Retain `native_pipe_probe.py` as an inert test fixture/spike until a separately reviewed Windows OS-local IPC mechanism satisfies the above. Prefer reusing mature verified primitives and the existing trusted host. Connect no production handler or auto-resume logic as part of CLI-2A. Independent exact-head code review and CI apply to this PR; there is no model/provider usage.

## Supervised Windows blocker investigation (2026-10-17)

At base HEAD `c9a250dfe40aae2027e3cf18e9c666dde976323e`, the scoped fallback adds negative platform tests and documents the observed gaps; transport code and authentication are unchanged. A safe Win32 replacement was not implemented or verified in this iteration. It would need explicit restrictive security attributes with effective DACL verification, local-client restrictions, PID attestation before any authentication/request exchange, and cancellable overlapped connect/read/write under one monotonic deadline. Every pending operation must be cancelled and completed before its buffers, event and pipe handles are freed. Using private stdlib listener internals in production or wrapping blocking authentication in a timed thread would not establish those properties.
