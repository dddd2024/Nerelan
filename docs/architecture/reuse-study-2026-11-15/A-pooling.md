## 0. What Magpie already gives (baseline for every verdict)

From `docs/architecture/MAGPIE_CAPABILITY_MAP.md` and a live `GET /v1/magpie/usage/requests` (500-row page):

- **In-request failover across accounts**: routing groups (`smart|order|rotate|usage|pace|weight|free|fast|cheap|drain|expiring`), `stays=auto` cache stickiness, auto-built `auto/<model>` groups, `provider fallback`. Nerelan never uses a group id (map §1.1, §2.2).
- **Stall bounds at the gateway**: `groupFirstToken`, `groupPatience`, `refusalRetries`, `retryAfterCap`, `noLoopGuard` (map §2.2). Not set by Nerelan.
- **Quota with reset times**: `/v1/magpie/quotas` with `limit`, `runsOutAt`; `quota wait`.
- **Per-request evidence**: each row carries `status`, `err_type`, `err` (upstream text), `providerAccount`, `session`, `ttft_ms`, `first_text_ms`, `tries`, `canceled`, `in/out/cache_read/cache_write`, `cost`, `credits`. All 186 `opencode` rows on the page carried a `session` id. The page held 7 OpenCode 429 rows (`rate_limit_error`, Raccoon "请求频率超限"). The OpenCode CLI retried these without telling the host (D1), but they *are* visible at the gateway within a second.
- **Raw upstream classes only**: `err_type` values seen: `402` (OpenRouter "Insufficient credits… never purchased credits"), `rate_limit_error`, `1005` (ZCode "exceed quota limit"), `6004`, `not_found_error`, `agent_canceled`, a Cloudflare 1010 URL. There is no normalised taxonomy (rate-limit vs quota-exhausted vs credits vs auth). The 14 OpenRouter 402 and 8 Groq 403 rows all came from `Python-urllib`, i.e. Nerelan's own probes (`pool_verifier.py`) re-asking dead bindings.
- **Hard budgets per gateway key**: `gateway-key issue --ttl --tokens --cost --models`, concurrency cap (map §2.4).
- **Not found in Magpie**: an *idle-between-chunks* stream timeout (only first-token `groupFirstToken`); automatic disabling of an account on a credits/billing error until a probe re-enables it; a documented use of upstream `Retry-After` / reset headers for account holds (only `retryAfterCap`, a cap).

Nerelan's overlapping code: `quota_guard.py` (161 lines; regex `ACCOUNT_LIMIT = api_error_429|rate_limit|usage_limit`, fixed `LIMIT_HIT_HOLD_SECONDS = 3600`, `PLAN_EXHAUSTED_HOLD_SECONDS = 5*3600`, reset from quota windows only when known), `model_router.py` (440; `weekly_pace_hold`, exclusions with `retry_at`), `pool_verifier.py` (130; one `Reply OK` probe per minute), `quota_reservation.py` (403; UNKNOWN settlement), `multi_account/cooldowns.py` (204), `model_availability.py` (149; overload regex).

## 1. one-api (songquanpeng/one-api)

- **What**: the original OpenAI-compatible key/channel distribution gateway. MIT, with a required attribution link. Go, single binary or Docker. Repo: https://github.com/songquanpeng/one-api
- **Maintenance**: **dormant**. Latest release v0.6.10 (Feb 2025). Last commits 2025-02-21 (https://api.github.com/repos/songquanpeng/one-api/commits). 941 open issues.
- **D2 (error classes)**: `monitor/manage.go` `ShouldDisableChannel`. 401 always disables the channel. Error types `insufficient_quota`, `authentication_error`, `permission_error`, `forbidden` and codes `invalid_api_key`, `account_deactivated` disable it, as do lowercase substrings `credit`, `balance`, `your credit balance is too low`, `已欠费`, `organization has been disabled`, `api key expired`. **429 is never a disable reason**; it only triggers retry on another channel (https://raw.githubusercontent.com/songquanpeng/one-api/main/monitor/manage.go). Re-enable through periodic channel tests (`CHANNEL_TEST_FREQUENCY`, `TEST_PROMPT`) and success-rate disable (`ENABLE_METRIC`, `METRIC_SUCCESS_RATE_THRESHOLD=0.8`) (README).
- **D1/D4/D9**: retry onto another channel by priority/weight; no reset-time handling, no stream timeouts found.
- **Verdict: COPY-DESIGN (a small part only)**. Use the three-way split: *credits/billing/auth* means disabled until a probe succeeds, *429* means retry elsewhere with a short hold, everything else means plain retry. Do not adopt the project: it is unmaintained and duplicates Magpie. Cost: about 50 lines in a classifier, no runtime.

## 2. new-api (QuantumNous/new-api)

- **What**: the actively developed fork of one-api ("developed based on One API (MIT)"). **AGPLv3**, which requires a visible link in modified UIs. Go/Gin backend, React 19 console, SQLite or Postgres+Redis, Docker-first, Electron wrapper. No documented Windows server install (https://github.com/QuantumNous/new-api).
- **Maintenance**: very active. v1.0.0-rc.51 on 13 Nov 2026, rc.50 on 12 Nov, rc.49 on 8 Nov. Commits on 2026-11-13 (https://github.com/QuantumNous/new-api/releases).
- **D2**: `service/channel.go` `ShouldDisableChannel`. It applies the global switch `AutomaticDisableChannelEnabled`, returns true for channel errors, false for skip-retry errors, then checks `ShouldDisableByStatusCode` and an Aho-Corasick search over `AutomaticDisableKeywords`. `ShouldEnableChannel` re-enables only `ChannelStatusAutoDisabled` channels after a clean test, under `AutomaticEnableChannelEnabled` (https://raw.githubusercontent.com/QuantumNous/new-api/main/service/channel.go). The defaults in `setting/operation_setting/status_code_ranges.go` are disable on `401` only and retry on `100-199,300-399,401-407,409-499,500-503,505-523,525-599`; `504`/`524` are never retried (https://raw.githubusercontent.com/QuantumNous/new-api/main/setting/operation_setting/status_code_ranges.go). Multi-key channels disable per key; rc.49 fixed a channel staying disabled after one key was re-enabled, and fixed manual disables being overridden by auto tests.
- **D1**: rc.38 added a "request policy" settings area (request checks, session/retry, channel health) that records policy decisions in usage logs (https://newreleases.io/project/github/QuantumNous/new-api/release/v1.0.0-rc.38). Explicit first-token or idle timeouts: not found.
- **D3**: per-token quota, usage logs and cache accounting (README). Refunds on failed async tasks (rc.47 `TASK_TIMEOUT_MINUTES`).
- **D4/D9**: channel affinity (sticky) with fallback that starts at the highest priority (rc.48), and priorities and weights. Cross-group retry on the `auto` group (v0.10.1).
- **Fit**: new-api is a Magpie *competitor* for API-key channels. It has no plugins for the subscription/free accounts Nerelan pools (WorkBuddy, Trae, Raccoon, Copilot, Codex, Claude logins); Magpie has those. Running both stacks would double the ops work.
- **Verdict: COPY-DESIGN** for two items: configurable *status-code ranges plus keyword list* as the account-error classifier, and **auto-disabled until a probe succeeds**, which differs from a manual disable. Do not run it. Cost: small.

## 3. LiteLLM Router / Proxy (BerriAI/litellm)

- **What**: Python SDK router and proxy server for 100+ providers. Core is MIT; the `enterprise/` features are commercial (for example tag budgets). Proxy features (virtual keys, spend logs) need a database.
- **Maintenance**: extremely active. v1.108.9 on 14 Nov 2026, v1.110.0-rc.3 and v1.111.0-dev.4 on 15 Nov (https://github.com/BerriAI/litellm/releases).
- **D1 (stalls, 429 in a CLI)**: `stream_timeout` is the "maximum time to wait for the first chunk"; `timeout` covers the whole response. On native `/v1/messages` and `/v1/responses` streams, `request_timeout` "bounds each wait for the next chunk", which is a true idle timeout. `keepalive_seconds` sends pings (https://docs.litellm.ai/docs/proxy/timeout). The router owns retries and sets provider `max_retries` to 0, so hidden client retries cannot happen (https://docs.litellm.ai/docs/routing).
- **D2 (classification, reset time)**: exception mapping turns 402 into `PaymentRequiredError`, distinct from `RateLimitError`; `BudgetExceededError` is proxy-only (https://docs.litellm.ai/docs/exception_mapping). Cooldown duration precedence: deployment `cooldown_time`, then the **provider's Retry-After**, then router `cooldown_time` (default 5 s) (https://docs.litellm.ai/docs/router/learn/reliability; origin PR https://github.com/BerriAI/litellm/pull/5358). Per-class thresholds `allowed_fails_policy` (`RateLimitErrorAllowedFails`, `ContentPolicyViolationErrorAllowedFails`, …) and per-class `retry_policy` (`RateLimitErrorRetries`, `AuthenticationErrorRetries`, `TimeoutErrorRetries`, …). Without `allowed_fails`, any 429 cools the deployment immediately (https://docs.litellm.ai/docs/routing). Daily caps `rpd`/`tpd` with `daily_reset_time`. LiteLLM does not parse vendor-specific reset bodies (for example Anthropic unified-reset): not found.
- **D3 (attribution)**: `LiteLLM_SpendLogs` per request with `spend`, tokens, `request_tags`, `metadata.attempted_fallbacks`; `spend_logs_metadata` or `x-litellm-tags` carry job/task ids; `/spend/logs/v2`; header `x-litellm-response-cost` (https://docs.litellm.ai/docs/proxy/cost_tracking). Whether failed requests are written with spend: not found.
- **D4 (move work off a dead account)**: `order` tiers, `fallbacks`, `context_window_fallbacks`, `content_policy_fallbacks`, `enable_weighted_failover`, `max_fallbacks` (https://docs.litellm.ai/docs/proxy/reliability).
- **D9 (allocation)**: `simple-shuffle` (weight/rpm/tpm), `usage-based-routing-v2`, `latency-based-routing`, `least-busy`, `cost-based-routing`, `routing_groups`; budgets `provider_budget_config` (`budget_limit`, `time_period`) and per-deployment `max_budget`/`budget_duration`, with over-budget deployments filtered out (https://docs.litellm.ai/docs/proxy/provider_budget_routing). Redis is needed for multi-instance state.
- **Fit**: LiteLLM would be a *second* gateway layer between OpenCode and Magpie, or a replacement for Magpie that lacks Magpie's subscription-account plugins. Executors are CLIs that call an HTTP gateway, so the Python Router library cannot sit inside their calls.
- **Verdict: COPY-DESIGN.** Take the cooldown precedence (explicit value, then upstream Retry-After/reset, then default), the per-error-class policy table, the 402-is-not-429 mapping, and the distinction between first-chunk and per-chunk-idle timeouts. Do not run it. Cost: design only. The classifier stays small.

## 4. Portkey Gateway (Portkey-AI/gateway)

- **What**: TypeScript gateway, MIT, `npx @portkey-ai/gateway` on :8787. "Gateway 2.0" pre-release merges the enterprise gateway into open source (https://github.com/Portkey-AI/gateway).
- **Maintenance**: moderate. Latest release v1.15.2 (12 Jan). Last commit on `main` 2026-05-25 (https://api.github.com/repos/Portkey-AI/gateway/commits). That is about 6 months without commits, though the 2.0 work may live elsewhere.
- **D1/D2**: `retry: {attempts ≤5, on_status_codes, use_retry_after_headers}`. Defaults are 429/500/502/503/504/529. It honours `retry-after-ms`, `x-ms-retry-after-ms` and `retry-after`, and **fails immediately if one Retry-After exceeds 60 s**, which keeps a request from silently waiting out a long quota (https://portkey.ai/docs/product/ai-gateway/automatic-retries). Circuit breaker `cb_config` (`failure_threshold`, `failure_threshold_percentage`, `cooldown_interval` ≥30 s, `failure_status_codes`, `minimum_requests`); if all targets are open the breaker is bypassed (https://portkey.ai/docs/product/ai-gateway/circuit-breaker). Whether this is in the OSS build: not stated.
- **D3/D9**: budgets/rate limits are in the hosted or enterprise product.
- **Verdict: KEEP out (no adoption).** The useful design point, "a long Retry-After fails fast instead of waiting", is already covered by Magpie's `retryAfterCap`.

## 5. Other active account poolers

- **CLIProxyAPI (router-for-me/CLIProxyAPI)**: MIT, Go. It pools **CLI OAuth accounts** (Codex, Claude Code, Gemini/Antigravity, Grok Build). Very active: v8.0.72 on 2026-11-14 (https://api.github.com/repos/router-for-me/CLIProxyAPI/releases). Config keys: `routing.strategy` (`round-robin|weighted-round-robin|fill-first`), `routing.retry.request-retry`, `max-retry-credentials`, `max-retry-interval`, `cooldown.transient-error-cooldown-seconds` (legacy 60 s), `cooldown.save-cooldown-status` (persists per-account cooldowns across restart, relevant to D4's reboot), `requests.streaming.bootstrap-retries` ("retries before first byte is sent", so failover is safe only before output), `keepalive-seconds`, legacy `quota-exceeded.switch-project/switch-preview-model` (https://raw.githubusercontent.com/router-for-me/CLIProxyAPI/main/config.example.yaml). **Verdict: COPY-DESIGN** of two points: *persist account cooldowns across restarts* and *retry on another account only before the first byte*. It overlaps Magpie otherwise.
- **claude-relay-service → sub2api (Wei-Shaw)**: CRS is MIT on Node+Redis. It has a published admin-auth bypass in ≤v1.1.248 and points users to sub2api (https://github.com/Wei-Shaw/claude-relay-service). sub2api is LGPL-3.0 on Go+Postgres+Redis, Linux/Docker only. It has sticky sessions, per-account concurrency, a "temporary unschedulable" error policy with custom codes, `Retry-After` honoured for Grok 429, soft per-key 5 h/day/7 d windows, and an explicit ToS/ban warning (https://github.com/Wei-Shaw/sub2api). **Verdict: KEEP out.** It overlaps Magpie, needs a heavier runtime, and its ToS risk is documented.
- **gpt-load (tbphp/gpt-load)**: MIT, Go. Multi-credential weights, retries, cooldown, blacklist, session affinity, credential probes. Thresholds and timeouts are not documented in the README (https://github.com/tbphp/gpt-load). **Verdict: KEEP out.** It is API-key only.

None of these supports Magpie's vendor-subscription plugins (WorkBuddy, Trae, Raccoon, SenseNova, MiniMax Code, Copilot). Replacing Magpie with any of them would lose the pool, which is the differentiator.

### Should Nerelan delete its account-level code?

Yes, for the *account* layer, staged behind the existing `account_routing=magpie` switch (`multi_account/routing.py`, never enabled):

- `quota_guard.py`: delete `account_refusal_hold`, `limit_hit_until`, `ACCOUNT_LIMIT`, the hold constants and `alternatives` for API/free bindings. Keep a much-reduced pre-dispatch check for **native Owner subscriptions** (Codex/Claude CLI logins), where pacing is an Owner rule, unless Magpie's `pace` strategy covers that.
- `model_router.py`: delete the per-account exclusions with `retry_at` and the proven-pool lock-in. Keep `capability`/`task_traits`/tier choice. The output becomes a Magpie group id, not a binding.
- `pool_verifier.py`: delete the reachability sweep; group failover makes per-binding proof unnecessary. Possibly keep a capability bake-off (#1527) as a separate feature.
- `quota_reservation.py`: delete the estimate-based `settlement`/`delta_calibration` UNKNOWN paths in favour of Magpie session rows; keep `admission`/`goal_fit` as task-level budget policy, which Magpie has no concept of.
- Also shrinkable: `multi_account/cooldowns.py`, the overload regex in `model_availability.py`.

Keep in Nerelan: tier/capability choice per task step, window/goal budgets, the evidence record, a thin session-row watchdog, and the error classifier over Magpie rows (Magpie's `err_type` is vendor-raw).

Risks: (1) group failover hides *which* account served the request, so Nerelan must read `providerAccount`/`served` per row for evidence and cross-model review independence (the reviewer's model family must still differ, so groups must be per model family). (2) Magpie is a single closed binary from one author, so lock-in is higher than with an OSS gateway; mitigate by keeping the `account_routing=auto` fallback path for one release. (3) `tries` was populated on only 1 of 500 rows, so failover evidence in the log is thin. Verify it before relying on it.

## Top 3 actions

1. **Route by Magpie group, not by account, and set the gateway stall knobs.** Enable `account_routing=magpie`; map each Nerelan tier to `auto/<model>` or a Nerelan-owned group with `stays=auto` and a spread/pace strategy; set `groupFirstToken`, `groupPatience`, `refusalRetries`, `retryAfterCap`. *Removes* D1a, D2b (account side), D4 (account side), and D9 lock-in/spreading. *Shrinks*: `model_router.py` (account exclusions, proven pool), `quota_guard.py` (holds), `pool_verifier.py` (reachability sweep, delete), `multi_account/cooldowns.py`. Cost: about 1–2 days, no new runtime; verify that Magpie switching works first (map §1.2).
2. **Settle and watch every attempt from Magpie's request log by `session`.** Charge actual tokens/cost from `/v1/magpie/usage/requests` rows, error rows included. Have the watchdog poll the same rows so a 402/429/quota row ends the attempt in seconds; optionally issue a per-task `gateway-key --ttl --tokens`. *Removes* D3 and most of D1a/D1b detection latency, and gives D2c its reason text. *Shrinks*: `quota_reservation.py` settlement/calibration, parts of `usage_ledger.py`/`magpie_settlement.py`, and the 900 s stall heuristic in `opencode_executor.py`. Cost: about 1–2 days.
3. **One table-driven error classifier over Magpie rows (one-api/new-api/LiteLLM design).** Classes are `rate_limited` (short hold, honour Retry-After/reset), `quota_exhausted` (hold until the Magpie `/quotas` reset), `credits_exhausted`/402 and `auth_or_entitlement` (disabled until a probe succeeds; never re-probe on a timer), `model_gone`/404, and `overload`. Keep a status-code range list plus a keyword list (`credit`, `balance`, `insufficient_quota`, `exceed quota`, `已欠费`, `频率超限`) as data, not code. *Removes* D2a and the 402 re-probe loop seen in the live log. *Replaces*: the regexes in `quota_guard.py` and `model_availability.py`. Cost: under a day. Also ask the Magpie author for a stream idle (between-chunk) timeout for D1b; not found in Magpie today.
