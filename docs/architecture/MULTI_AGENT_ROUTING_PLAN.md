# 多 Agent 协作与按任务选模型：现状与改进规划（2026-11-09，待 Owner 确认）

## 1. 原规划：角色只是过渡

| 时间 | 决定 | 来源 |
|---|---|---|
| 2026-10-14 | 固定五档角色（planner / complex / coder / simple / reviewer → roster 绑定）作为基线跑完 #1164；下一轮改为"按任务需求与成本动态选模型"，角色只保留为兼容字段和回退 | #1165 |
| 2026-10-19 | 每个任务按难度（1–5）和类型（code / analysis / writing / research_design / review），在全部可运行绑定里选"能力档 ≥ 难度的最便宜候选"；roster 变成可选，只作钉死 | #1244 |
| 2026-10-19 | 选路还要看上下文大小、模型特性（工具调用可靠性、拒答）、额度；拒答是选路信号而非失败 | #1248 |
| 2026-10-19 | 能力档的初值来自多个公开基准，再用真实结果修正（先验当作少量伪观测） | #1264 |
| 2026-10-21 | 长跑卡在"唯一合格模型额度不足"：补能力证据、额度校准、规划时把任务切小、额度等待时改选其他模型 | #1313 |

## 2. 现状（main `5dcb1da8`）

### 已经落地

- 选路已是**按任务**的：`trusted_host._resolve_task_model` → `model_router.select_model`，硬过滤
  （执行器、Owner 覆盖、上下文窗口、额度与周配速、拒答、评审 ≠ 作者）后按能力档、成本、实测成功率打分，
  决策写入 `MODEL_SELECTED`（#1244、#1248、#1268）。
- 失败按能力档升级重试，额度等待会改选同档或更高档（#1280、#1313 D）。
- 规划器输出难度、类型、上下文需求和能力需求；角色在提示里标为"Legacy roles (optional)"。
- 评审任务、产物交接、评审→修复循环（最多 3 轮）、多账户反馈调权重均已实现并有测试。
- 基准快照 `capability_benchmarks_snapshot.json`（public-leaderboards@2026-10-20，16 个模型家族）随包发布，
  采用需要 Owner 确认摘要（#1264）。

### 角色仍在起作用的地方（过渡的残留）

| 位置 | 作用 | 问题 |
|---|---|---|
| `agent_roster.json` + `_resolve_agent_role` | 角色只用于"钉死"（`pin`）；规划器、旧路径仍经过它 | 自然语言配置器仍写角色→模型映射，Owner 以为在分工，实际只影响钉死 |
| `model_router`：`role == "planner"` 只能用 `codex` / `claude_code` | 规划器跑在原生 CLI 的只读工作树里 | Claude 用尽、Codex 受配速时**无法规划**，只能手写任务 |
| `GoalService._task_route` 的 roster 回退 | 没有任务级选路器时按角色派 | 生产宿主不走这里，只剩测试与兼容 |
| `LEGACY_DIFFICULTY` | 旧计划只有角色时换算成难度 | 合理的兼容，可保留 |

### 真实运行里的情况（2026-11-09 第一批窗口）

- 运行宿主**没有采用基准快照，也没有 `model_capabilities.json`**，所以每个模型的能力档都是先验 2、`unproven`；
  难度 3 的任务没有合格候选，选路只能在免费模型里按成本挑，6 个任务全落在 `glm-5.2`
  （`prior_only_unproven`）。这正是 #1313 原因 1，在这台宿主上仍未解决。
- 一句话成稿绕过了规划器，每个目标只有一个难度 3 的 `implement` 任务：没有评审、没有拆分、
  上下文需求和能力需求都是 0，按任务选路的信息基本没用上。
- 并发 1，任务排队执行。

结论：按任务选路的机制已经替代了角色，但**缺能力证据、缺规划、缺评审任务**，实际效果接近"所有任务给同一个免费模型"。

## 3. 改进规划

### 阶段 A：让按任务选路有依据（不扩大权限，优先做）

| # | 内容 | 谁做 | 规模 |
|---|---|---|---|
| A1 | 在运行宿主采用基准快照：`capability_benchmarks stage` → Owner 核对差异并 `adopt --confirm <digest>` | 监督者准备，Owner 确认摘要 | 小 |
| A2 | 快照补别名并刷新：`token-sensenova/glm-5.2`、`workbuddy/hy4free`、`trae-cn/Doubao-Seed-2.1-Turbo` 等现用模型要能解析到家族；无条目的列为 `needs_benchmark` | Nerelan（Issue） | 小 |
| A3 | 账户页显示每个绑定的能力档、来源（基准 / 实测 / 先验）和置信度，让 Owner 看到选路依据 | Nerelan（Issue） | 中 |
| A4 | 第一批窗口结束后，用窗口报告（N3）核对：各模型实测成功率是否已回写到画像 | 监督者 | 小 |

### 阶段 B：恢复规划与评审，让一个目标真的由多个 Agent 完成

| # | 内容 | 谁做 | 规模 |
|---|---|---|---|
| B1 | 规划器不再限定 Claude/Codex：允许 OpenCode 在只读工作树里规划（按难度 4、类型 research_design 选路），保留"只读、只输出 JSON、过 GoalService 校验"的约束 | 监督者（涉及执行器沙箱，按 R2 同等审查） | 中 |
| B2 | 一句话成稿：规划器可用时走规划器；不可用时用固定模板"实现（带 `validation_checks`）+ 评审（`kind=review`、`artifact_input`）"，评审必须选到与作者不同的模型家族 | Nerelan（Issue），依赖 #1410 | 中 |
| B3 | 规划器按 Issue 内容估计难度和上下文需求，不再一律 3 | 随 B1 | 小 |
| B4 | 预设"一天"改为并发 2（同一窗口内两个目标并行），文件冲突由现有工作区隔离保证 | Owner 决定 | 小 |

### 阶段 C：退役角色，验证收益

| # | 内容 | 谁做 |
|---|---|---|
| C1 | roster 只保留"钉死"语义：界面改名为"固定模型"，自然语言配置器改写为 Owner 覆盖（排除、最高难度、允许内容）而不是角色映射；`_task_route` 的角色回退只留在测试 | Nerelan（Issue） |
| C2 | #1165 的对照实验改为"单 Agent vs 实现+评审团队"：同一组真实 Issue、同一基线，比较独立验收通过率、每个通过任务的完整成本（含重试和评审）、耗时；10 个任务以内只报告结果，不下改善结论 | 监督者设计，Nerelan 执行 |
| C3 | 对照数据接入 `orchestration_selector` 的实测分支，让平台按数据为目标选单 Agent 还是团队 | Nerelan（Issue），在 C2 有数据后 |

### 不做

- 不恢复固定角色分工；不新增第二套选路器；不引入新的多 Agent 框架（沿用 LangGraph 团队运行时与现有 GoalService）。
- 不为凑多 Agent 而给小任务强加评审：单文件文档或测试改动可以只有一个任务，由 C2 的数据决定。

## 4. 与当前阶段的关系

A1 在第二批窗口激活前完成，这样第二批开始就有能力依据、有评审任务。
