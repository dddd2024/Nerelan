# 一句话启动：简化无人值守运行的入口（待 Owner 确认）

目的：让 Owner 像使用普通 Agent 工具一样开始工作——在输入框写一句话，看一张确认卡片，点一次确认——
同时保留无人值守运行必需的边界：授权有期限、开销有上限、授权确实来自 Owner。

## 1. 为什么要做

2026-11-08 启动首次真实任务长跑，从写好方案到窗口真正跑起来用了约一个小时，期间遇到的问题：

| 问题 | 性质 | 本方案是否解决 |
|---|---|---|
| 目标只能用脚本直接写入任务库，没有界面入口 | 产品缺口 | 是：输入框直接生成可激活的目标 |
| `single` 模式、未钉死模型的目标在 Owner 窗口里没有绑定，首个任务被拒绝派发，窗口 BLOCKED | 产品缺陷 | 是：启动时统一选路，且激活前预检 |
| 激活前不知道每个任务会用哪个模型（实际选了最弱的 flash-lite） | 产品缺口 | 是：确认卡片逐任务显示所选模型 |
| 9 月遗留的 3 个 ACTIVE 认领挡住激活，只能改用独立数据目录 | 产品缺口 | 部分：激活前预检把它列为明确原因，并给出处理入口 |
| 确认码输入时被告警日志打断，输错一次 | 产品缺陷 | 是：确认改在界面或原生对话框里完成 |
| 环境变量、启动脚本、数据目录要手写 | 产品缺口 | 是：运行配置随窗口保存，开机恢复用同一份 |
| Bash 沙箱把 AppData 写入重定向到副本 | 操作环境问题 | 否：与产品无关，已记录 |

"窗口 + 上限 + 一次授权"本身保留：它们是"中途不打扰 Owner"的代价。要去掉的是围绕它们的手工步骤。

## 2. 现状（main `4d4077f6`）

| 入口 | 现状 | 依据 |
|---|---|---|
| 首页输入框（GoalComposer） | 只创建草稿目标，跳到审批页 | `frontend/src/routes/home.tsx`、`lib/goal-start-operation.ts` |
| 审批页 | 能规划、批准；启动前调用 `/api/windows/activate`，未钉死权限时服务端一律拒绝（`owner_selection_confirmation_unavailable`），前端没有对应提示 | `lib/goal-continuation-operation.ts`、`task_service.py` 激活路由 |
| 新建任务 | 不需要窗口，直接执行；默认执行器是测试用的 `deterministic_fixture` | `hooks/use-tasks.ts`、`/api/tasks/<id>/execute` |
| Owner 窗口（#1401） | 命令行 + 终端确认码；多目标、最长 7 天 | `owner_window.py` |
| 原生对话框（#1207） | 系统对话框确认，校验交互式会话与 SID；只允许 1 个钉死的 Codex 任务、30 分钟、不重试 | `native_owner_dialog.py`、`docs/host-native-dialog-gate.md` |
| 规划 | 确定性规划无需模型；Agent 规划仅 `agent_team`，需要 Codex/Claude 登录，不需要窗口 | `goal_service.py`、`agent_planner.py` |
| 窗口参数预设 | 没有；界面硬编码 20/2/1 且会被服务端拒绝 | `platform-client.ts` |

结论：界面能走到"批准"，但走不到"开始"；能开始的路径（Owner 窗口命令行）又没有界面。

## 3. 目标体验

1. **一句话**：在首页输入框写"修复 #1350、#1285、#1336，跑一天"。Issue 链接、编号或自由描述都可以。
2. **自动成稿**：系统拆成目标（每个 Issue 一个，或一个目标多个任务），用确定性规划生成任务；需要时
   可选 Agent 规划。全部以 `agent_team` 或钉死绑定建立，保证启动时每个任务都有模型。
3. **确认卡片**：一屏显示——
   - 目标与任务（Issue 标题、范围规则）；
   - **每个任务将使用的模型**，以及模型池（免费 / 订阅 / 受周配速约束 / 付费已排除）；
   - 预设的窗口参数（见第 4 节），可展开修改；
   - **预检结果**：遗留认领、额度、执行器可用性、仓库状态，有阻塞时直接说明原因和处理方式。
4. **一次确认**：Owner 在宿主自己的确认界面上点"确认"（见第 5 节），窗口激活、任务开始。
5. **之后不用管**：告警弹通知；结束时生成一份报告（完成了什么、开了哪些 Draft PR、用量、失败原因）。

另设 **交互模式**：Owner 在场、看着它干活时不需要窗口和激活，沿用"新建任务 → 直接执行"，
但默认执行器改为真实执行器，并在界面上明确标注"此模式需要你在场"。

## 4. 预设

| 预设 | 时长 | 并发 | 重试 | Token 上限 | 付费 API | 产出 |
|---|---|---|---|---|---|---|
| 试跑 | 2 小时 | 1 | 1 | 300,000 | 关 | Draft PR |
| 一天（默认） | 24 小时 | 1 | 2 | 2,000,000 | 关 | Draft PR |
| 一周 | 7 天，按天续期 | 2 | 2 | 10,000,000 | 关 | Draft PR |

预设值存在 Owner 配置里，可改；数据库对窗口的硬上限不变。只开 Draft PR 是所有预设的默认，
自动合入另行授权。

## 5. 确认方式：谁能证明是 Owner

项目有意不让浏览器渲染端直接授权（`docs/owner-selection-trust-gap.md`）：渲染端可能被劫持，
它说"Owner 已确认"不算数。所以"点一下确认"必须发生在宿主控制的界面上。

| 方案 | 强度 | 改动 | 建议 |
|---|---|---|---|
| A. 原生对话框（扩展 #1207） | 与现在的终端确认码相当：证明交互式会话里有人点了确认，防不住同用户自动化 | 去掉"1 个 Codex 任务、30 分钟"的限制，改为显示多目标范围摘要并链接完整范围；激活走 Owner 窗口同一套原子事务和回执 | **推荐**，第一步 |
| B. 界面发起 + 原生对话框确认 | 同 A | 界面点"开始"只请求宿主弹出对话框，界面本身不携带授权 | 与 A 同时做，作为界面入口 |
| C. 系统身份验证（Windows Hello / 密码） | 更强：证明是这个用户本人 | 需要接 Windows 安全 API | 后续 |
| 保留终端确认码 | 同 A | 无 | 作为无界面时的备用入口 |

范围太长不能完整放进对话框时，对话框显示摘要和完整范围的摘要哈希，完整范围在界面卡片里；
宿主在事务里比对哈希，与现有"打印前读取、事务内逐字节比对"的做法一致。

## 6. 实施

| 步骤 | 内容 | 风险级别 | 估时 |
|---|---|---|---|
| 1 | Owner 窗口启动前对每个任务选路，任何任务无绑定则拒绝激活并列出原因（修复本次 BLOCKED 的根因） | R1 | 0.5 天 |
| 2 | 激活前预检接口：遗留认领、执行器、额度、模型池，供命令行和界面共用 | R1 | 1 天 |
| 3 | 输入框一句话成稿：识别 Issue 链接/编号，抓取标题正文，建 `agent_team` 目标并确定性规划 | R1 | 1 天 |
| 4 | 预设与确认卡片（只读展示 + 参数修改），前端测试与视觉基线 | R1 | 1.5 天 |
| 5 | 原生对话框确认扩展到多目标 Owner 窗口（方案 A/B），沿用原子激活与回执 | 授权扩展，需 Owner 决定与独立评审确认不削弱现有控制 | 2 天 |
| 6 | 运行配置随窗口保存，开机自启读取它，替代手写环境文件 | R1 | 0.5 天 |
| 7 | 结束报告：完成项、Draft PR、用量、失败分类 | R1 | 1 天 |
| 8 | 交互模式：默认真实执行器，界面标注"需要在场" | R1 | 0.5 天 |

合计约 8 个工作日，可在长跑间隙推进；步骤 1、2 优先，因为它们直接减少长跑启动失败。

## 7. 验收

- 从输入一句话到窗口激活，Owner 只需一次确认，不打开终端、不写文件。
- 任何会导致启动后立即失败的情况（无绑定、遗留认领、执行器不可用、额度不足）都在确认前显示，激活被拒绝而不是窗口 BLOCKED。
- 确认卡片里的模型与实际派发使用的模型一致（与执行前模型池核对同源）。
- 渲染端无法单独激活窗口：没有宿主确认界面上的确认，激活请求一律拒绝。
- 开机恢复不需要额外配置。

## 8. 需要 Owner 确认的事项

1. 确认方式先做方案 A + B（原生对话框，界面只负责发起），终端确认码保留为备用。
2. 第 4 节三个预设及其数值。
3. 实施顺序：先做步骤 1、2，再做其余。
4. 交互模式是否需要，以及默认执行器用哪个免费模型。
