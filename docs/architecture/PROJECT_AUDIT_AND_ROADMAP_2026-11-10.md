# 项目全面审计与路线规划（2026-11-10，待 Owner 确认）

基线：`main@b6bc3236`。审计方式：阅读代码结构、文档、CI、开放的 Issue/PR 和最近两份交接；没有改动代码。
本文是建议，不是授权；其中涉及删除、归档、改治理文件的项都需要 Owner 单独决定。

## 0. 目标

- **近期**：多 Agent、能自我进化、用起来像常见 agent 工具的工具。
- **长期**：住在电脑里的全能助手，能写代码、做视频、打游戏等。

## 1. 结论

1. **现在的 Nerelan 是一条"受治理的代码交付流水线"，不是通用 agent 工具。** 目标 → 计划 → 执行器 →
   校验 → 独立评审 → Draft PR 这条链路是通的，控制面（授权窗口、额度、恢复、证据）做得很深。
2. **控制远多于被证明的能力。** 第一批真实任务：6 个目标 5 个到 READY，独立评审 3/4 通过，1 个假成功，
   1 次池外升级，约 1960 万 token；此前两次激活都被平台自身缺陷挡住。毕业标准未达到。
3. **离"像常见 agent 工具"差的是交互，不是治理。** 没有对话式会话、运行中纠偏、按评审/CI 意见继续改这三样。
4. **离"全能助手"差的是任务模型。** 任务契约写死为"git 仓库 + 改动文件 + Draft PR"，
   非代码任务没有产物类型、验收方式和工具层。相关 Issue（#785、#790、#802、#814）都还在规划状态。
5. **"自我进化"目前只有数值校准**（能力档、成本率、单/多 Agent 盈亏点），没有"失败 → 教训 → 下次不再犯"
   的闭环；发现平台缺陷、建 Issue、评审、落地都靠监督者（Claude）手工完成。
6. **历史负担重。** 约 20 万行 Python 里，当前产品（`platform_v1` + `model_access`）约 6.5 万行；
   其余大部分是逆向工具和 v1 治理的遗留，仍在 CI 的必过检查里。

## 3. 架构方向

三条原则，后面各阶段都按它来：

1. **内核只管四件事：任务真相、授权与预算、验收、证据。** 这是 Nerelan 自己的价值，保持不变。
2. **能力通过"领域包"扩展，不改内核。** 一个包 = 工作区类型 + 可用工具 + 产物类型 + 验收方式。
   代码开发是第一个包（现有全部逻辑）；视频、网页操作、桌面操作是后续的包。
3. **工具和运行时继续复用。** 工具层用 MCP（OpenCode、Claude Code、Codex 都已支持），由宿主决定每个任务
   开放哪些工具；桌面和浏览器控制用执行器已有的能力，不自研。

对应的最小改动：把 `ExecutorResult` 的"改动文件 + 校验退出码"推广为"产物列表 + 验收结果"，
Draft PR 变成代码包的发布方式之一（#814 是入口）。

## 4. 路线

### 阶段 0：把当前阶段做完（约 2 周）

目标：一句话启动可用，监督达到毕业标准。内容沿用 `ONE_STEP_START_NERELAN_RUN.md` 和交接文档，不新增范围。

- 落地 #1426、#1421、#1423、#1431；更新运行宿主（需要 Owner 同意重启）。
- 修 #1427（零改动判失败）、#1428（升级不出池）、#1429（积分配速）；采用基准快照。
- 第二、三批（N1、N2、N6–N8）。
- **完成标准**：连续 3 批首次 ACCEPT ≥ 80%、无假成功、无平台缺陷导致的停窗。

### 阶段 1：用起来像 agent 工具（约 4 周）

- **会话**：任务详情页可以对话；运行中纠偏（#795）；按评审和 CI 意见继续改同一个分支（#791、#1251）。
- **入口**：命令行 `nerelan "<一句话>"`，与界面共用同一套接口（#1198、#806）。
- **小任务快路径**：在场的交互任务不必开 Owner 窗口，用现有交互模式加默认预算。
- **瘦身**（需要 Owner 决定，见第 6 节）：遗留逆向代码和 `project_state/` 移出 `main`；CI 必过检查只留现行产品；
  更新 README；写一份单一的"现状与路线"文档替代过期路线图；清理停滞的 Draft PR 和 Planning Issue。
- **完成标准**：Owner 一周内的日常小改动有一半以上经 Nerelan 完成，且不需要打开终端。

### 阶段 2：真的多 Agent，真的自我进化（约 1–3 个月）

多 Agent（沿用 `MULTI_AGENT_ROUTING_PLAN.md` 的 A/B/C）：

- 规划器可以用任意执行器；默认"实现 + 评审"模板（#1430 已落地）；并发 2。
- 做单 Agent 对团队的对照实验（#1267），用数据决定什么任务用团队。

自我进化，分四层，从便宜的做起：

| 层 | 内容 | 现状 |
|---|---|---|
| 参数 | 能力档、成本率、盈亏点由实测更新 | 有机制，运行宿主未启用 |
| 教训 | 每个窗口结束后，按失败分类生成教训，按仓库保存，由 `context_builder` 注入后续任务 | 无 |
| 技能 | 重复成功的做法沉淀为技能文件（与执行器的 skill 格式兼容），按任务类型加载 | 无（只有旧的逆向提示） |
| 自修 | 窗口报告里的平台缺陷自动建 Issue 和 Goal，Nerelan 自己修，走同一套评审和落地 | 现在由监督者手工做 |

边界：自修只限 R1；`AGENTS.md`、工作流、`landing_review.py` 不允许自改；每条教训和技能可追溯到产生它的任务，可以关闭。

- **完成标准**：首次 ACCEPT 率和"每个通过任务的 token"连续 4 批改善；至少 3 个平台缺陷由 Nerelan 自己发现并修复落地。

### 阶段 3：走出代码（约 3–6 个月）

- 先补安全（这是前置条件）：本地客户端认证 #384、发布前密钥扫描 #447、工具出站限制、模型上下文隐私 #798。
- 任务契约推广为"产物 + 验收"（#814）；工作区可以不是 git 仓库（#809）。
- 工具层：MCP 生命周期与授权（#790）；浏览器执行器（#802）。
- **第一个非代码包建议做视频**：流程可以拆成脚本 → 配音/素材 → 剪辑合成（ffmpeg）→ 检查，
  每一步都有可以机器验证的产物（时长、分辨率、字幕对齐、音量），最接近现有的"确定性验收"。
  数学建模包（#407）是另一个现成候选。
- **完成标准**：一句话产出一个通过自动检查、Owner 认可的短视频，全程有产物和成本记录。

### 阶段 4：常驻助手（约 6–12 个月）

- 常驻服务 + 托盘/桌面壳（#585）；通知与收件箱；定时和事件触发的目标。
- 长期记忆：Owner 偏好、常用项目、历史决定，可查看、可删除。
- 桌面控制执行器（#785），按应用授权。
- 游戏：从单机、回合制或慢节奏游戏开始。实时游戏需要低延迟的本地视觉模型，大模型的响应时间不够；
  联网游戏涉及反作弊和服务条款，不建议做。

## 5. 不建议做的

- 在阶段 0 完成前开新方向；项目已经换过四次重心（逆向工具 → 治理 → 开发平台 → 多账户），每次都留下一层代码。
- 自研工具协议、桌面控制、浏览器自动化或新的多 Agent 框架。
- 再加治理机制。现有控制已经超过被证明的能力，接下来该补的是能力和结果数据。
