## 2. Magpie M0 source API mappings (exact)

All calls are loopback GETs with `Authorization: Bearer magpie-nerelan`, 2 s timeout
(`magpie.py:fetch_magpie_snapshot`, lines 185–229):

| Magpie endpoint | Nerelan parser | Normalized fields | Failure handling |
|---|---|---|---|
| `GET /api/hello` | `parse_hello` — requires `{"name":"magpie"}`; version must not embed private strings | `version` (e.g. `0.1.1250`); non-Magpie ⇒ snapshot `status="not_magpie", reason="invalid_hello"` and **no further requests** | JSON/decode failure ⇒ `not_magpie` |
| `GET /v1/models` | `parse_models` — requires `object=="list"` + `data[]` | per model: `model_id`, `provider` (prefix before `/`, else `owned_by`), `display_name`, `reasoning` (bool), `context_window`, `max_output_tokens`, `is_group` (no `/` in id) | Malformed ⇒ `[]`; ids containing private strings (`user`/`alias`/`from` values) are dropped |
| `GET /v1/magpie/quotas?kept=1` | `parse_quotas` (cached-only read; `kept=1` requests cached readings; vendor-refresh behavior has not been independently tested here) | per account: `provider`, `kind` ∈ {subscription, plan, balance}, `plan`, `account_ref` (12-hex SHA-256 of `[provider, user]`), `windows[]` (`name`, `used_percent`, `remaining_percent` ≤100, `resets_at`, `unlimited`), `state` (`FRESH` <15 min old, `STALE`, `UNDATED`, `UNKNOWN`), `reason` (`invalid_schema`, `quota_error`, `read_deferred`, `invalid_timestamp`, `stale_reading`, `missing_windows`, `invalid_window`, `no_read_time`, `duplicate_account`), `observed_at` (min of `readAt`/`asOf`), `provenance` `EXTERNAL_MAGPIE`, `source_version` | 403 `gateway_key_held` ⇒ that account unavailable; redirect (3xx) refused; transport error ⇒ `status="unavailable", reason="request_failed"` with the error text discarded (privacy) |

Privacy intention (static source evidence, not end-to-end proof): `_private_strings` and `_text` in `magpie.py:33–49` filter names, aliases and source strings from recognized response fields. Complete recursive output-path tests and live error-path checks remain necessary. The 12-hex `account_ref` is deterministic and pseudonymous (not anonymous); it can be linkable or guessable for predictable accounts.

## 3. Data provenance summary

- **Nerelan-side figures** (`observed_usage`, `token_usage`, `equivalent_cost`): `LOCAL_METERING` / `ESTIMATED_LIST_PRICE` over the last 500 finished model-backed tasks (TaskStore), plus vendored pricing snapshot. Never from Magpie.
- **Official CLI quota** (Codex/Claude accounts): `OFFICIAL_VIA_CLI` from CLI session logs / status line / captured notices; opt-out env var.
- **Magpie figures**: `EXTERNAL_MAGPIE`, cached-only gateway readings, ≤15 min freshness window, carried version. Listed **only** under `external_sources.magpie`.

## 4. Possible double counts — analysis

1. **Magpie accounts vs Nerelan connections** (the designed case): `resources.py:_read_external` (lines 125–135) returns the snapshot as a separate mapping, and `build_resource_view` never reads it when computing any connection's `quota`, `token_usage`, `tokens` or `equivalent_cost` (verified: `external` is only assigned to `view["external_sources"]`, line 231–232). No double count on this path.
2. **Same subscription reachable both ways** (e.g. a WorkBuddy account signed into a CLI *and* pooled in Magpie): the CLI-side quota would appear under that connection's `quota` and again under `external_sources.magpie`. Since the API listings are structurally separate but the Magpie snapshot is not currently rendered in the UI, a reader summing them across sections could double count. No dedup key exists (the CLI path has no account id; Magpie has only `account_ref`). Status: **possible, unmitigated; the Owner has not explicitly accepted this residual risk** (the doc says external accounts are "never added into a Nerelan connection's quota, tokens or cost").
3. **Tokens/cost of tasks routed through a Magpie-backed Connection**: counted once by the ledger as ordinary local metering. But the *same underlying spend* may also appear inside Magpie's own account windows (`used_percent`). Since Nerelan shows Magpie windows as percentages and its own usage as token counts / list-price USD, they are not added numerically anywhere in code. Residual risk: a human reading "used_percent 20%" plus "$16.67 estimated" as independent amounts. **No numeric double count found in source.**
4. **Magpie's `GET /v1/magpie/usage`**: not called by Nerelan at all, so no usage-side overlap exists.
5. **`quota_known` summary** counts only connections whose own `quota.state == "OBSERVED"` (resources.py:226); Magpie accounts do not inflate it.

## 5. Failure modes (per component, current source behavior)

- **Magpie gateway down / wrong port**: `fetch_magpie_snapshot` ⇒ transport failures produce `status="unavailable", reason="request_failed"`, while invalid URLs produce `status="refused", reason="invalid_url"`; `/api/resources` still 200 with `external_sources.magpie.status` reflecting the specific failure reason; all legacy figures intact (documented invariant, fixture-tested).
- **Not Magpie on that port**: `not_magpie` after `/api/hello`; models/quotas never requested.
- **Redirect**: refused (`redirect_refused`).
- **Stale cache** (>900 s): account `state="STALE"`, reason `stale_reading`, windows cleared.
- **Undated readings** (`readAt`/`asOf` absent): `state="UNDATED"`, reason `no_read_time` — windows kept, age unknown.
- **Duplicate account entries** (same `account_ref` twice): forced to `UNKNOWN`/`duplicate_account` (magpie.py:174–181).
- **Held key (403 `gateway_key_held`)**: account reported unavailable.
- **Observed-usage source failure** (profiles callable raises): resources still listed, `observed_usage.status="unavailable"`, zero totals (resources.py:70–76).
- **Quota source failure**: only that connection's quota drops to `UNKNOWN`; request does not fail.
- **Quota guard with unknown windows**: decision `ok`, reason `quota_unknown` (quota_guard.py:63) — i.e. it never blocks on missing data; a Magpie-routed subscription can be dispatched while its Magpie window is actually exhausted (the CLI will then error; `LIMIT_HIT` regexes catch `api_error_429|rate_limit|usage_limit` and start a hold — but only for accounts Nerelan recognizes, see next).
- **Guard blind spot**: `check()` returns `None` for any non-`NATIVE_CLI_PROVIDERS` connection (quota_guard.py:58), so Magpie-routed subscriptions are unguarded pre-dispatch; a mid-run 429 surfaces as a normal executor failure. Whether the executor's error text for a Magpie upstream matches `ACCOUNT_LIMIT` is **unknown** (not verifiable without a live gateway).
- **Coexistence risk (from docs, unverified)**: tools like Magpie rewriting `~/.claude/settings.json` `env` may redirect a Nerelan Claude account run without Nerelan's binding/lease/budget knowing; `--setting-sources` pinning is listed as remaining P0-3 work, status unknown at this head.
