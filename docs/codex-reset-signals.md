# Codex 提前重置信号

Codex 有时会在周窗口结束前全局重置额度，由 OpenAI 的 Tibo（@thsottiaux）在 X 上宣布。
宣布后剩余的周额度会被重置作废，所以这段时间应当把 Codex 用到只剩一点，而不是继续按周配速节省。

## 规则（Owner 决定，2026-11-07）

| 情况 | 选路行为 |
|---|---|
| 收到有效公告，在预计重置时间之前 | 周额度配速让位，允许用到只剩 `reset_buffer`（3%），沿用既有 drain 规则（#1248、#1281） |
| 到达预计重置时间 | 信号失效，回到正常配速 |
| 账户的周窗口已在公告之后重新开始 | 立即回到正常配速，不管公告怎么说：重置已经发生，继续放开会花掉新一周的额度 |
| 没有公告、来源不可用、数据过期 | 视为没有公告 |

只作用于 Codex。Claude 不会因 Codex 的公告放开。用到只剩 3% 而不是 0，不会触发 Codex 的积分消耗。

## 预计重置时间

按以下顺序取第一个可用的：

1. 公告或同一次公告里的回复明确写出的时间，按发帖时间往后推算：`by midnight PST`、`at 10am PT`、
   `by 18:00 UTC`、`in 2 hours`。时区按洛杉矶、纽约或 UTC 换算，含夏令时。没有时区、含糊或超过 72 小时的说法不采用。
2. 只说 `today is a reset`：当天太平洋时间午夜。
3. 都没有：公告后 24 小时，可用 `REVERSE_AGENT_CODEX_RESET_WITHIN_HOURS`（1–72）调整。

同一次公告：最新公告 12 小时内的公告类帖子、源站的重置事件，以及这段时间里的回复，都归为同一次。
时间常写在回复里，比如 10-28 那次是先发 "today is a reset"，45 秒后回复 "Lands by midnight PST."。

## 公告来源

公开镜像 `https://codex-reset.com/api/feed`。直接匿名访问 X 返回 403。只读、5 秒截止、256 KiB 上限、拒绝重定向，
不携带任何凭据，也不调用模型。识别依据两部分：

- 源站自己的 `events` 分类：`type=reset`、`scope=global`、非 banked、置信度为 medium/high、不是预告，链接是 Tibo 的原帖。
- Tibo 的帖子：源站标记的明确重置声明，或原帖（不是回复）里 "today is a/the reset" 这一陈述。
  问句和否定不算；banked、预告和范围不明的声明不算。

源站 `effective_at` 字段目前总是空的，所以不依赖它。

## 运行

宿主环境设置 `REVERSE_AGENT_CODEX_RESET_WATCH=1` 启用，默认关闭。读取器缓存结果，至多每 15 分钟在后台请求一次，
选路从不等待网络。当前信号显示在账户页。

## 验证

```bash
python -m pytest tests/platform_v1/test_codex_reset_signals.py tests/platform_v1/test_weekly_quota_pacing.py -q
```

用 2026-11-07 下载的真实数据回放了 10 月的两次重置：10-28 在公告后放开，07:00 UTC（太平洋时间午夜）结束；
10-26 只说了 "today is a reset"，同样在 07:00 UTC 结束。回放数据不在仓库里，测试用的是按真实帖子结构构造的离线样本。

## 修正记录

本模块最初来自草稿 PR #1247，这里修正了三个问题：

- 在 CPython 3.13 上拿不到 socket 就直接放弃，导致真实环境里永远返回 UNKNOWN。现在由外层 5 秒截止保证不阻塞。
- 只认源站标记的"明确声明"，10 月真实的两次公告都没被标记，因此都会漏掉。
- 没有接入选路，也没有时间，无法支持重置前放开。
